# 第 2 章：图形渲染管线

> 来源：《Real-Time Rendering, Fourth Edition》Chapter 2  
> 学习状态：已完成首次阅读

## 一句话概括

实时渲染管线把场景中的相机、几何、材质和灯光，持续转换为二维图像。CPU 决定这一帧提交什么，GPU 负责把三角形变换、光栅化、着色并写入显示缓冲。

```text
场景数据
  │
  ├─ 应用阶段（CPU）：更新场景、选择并提交待画图元
  └─ GPU：几何处理 → 光栅化 → 像素处理/合并 → Back Buffer → Present
```

## 2.1 架构

### 四个功能阶段

| 阶段 | 主要位置 | 回答的问题 | 典型工作 |
| --- | --- | --- | --- |
| Application | CPU（也可借助 GPU Compute） | 这一帧要画什么？ | 输入、游戏逻辑、动画、物理、剔除、提交绘制命令 |
| Geometry Processing | GPU | 三角形在相机看来在哪里？ | 顶点处理、投影、裁剪、屏幕映射 |
| Rasterization | GPU 固定功能硬件为主 | 三角形覆盖哪些采样点？ | 三角形设置、遍历、插值、生成片元 |
| Pixel Processing | GPU | 这些片元是什么颜色，能否写入画面？ | 像素着色、深度/模板测试、混合、写入缓冲 |

### 管线思维

- 管线提高的是**吞吐量**：当前一帧的后段在工作时，后续工作可在前段开始准备。
- 最慢阶段是**瓶颈**，决定整帧的最高速度。
- 60 FPS 的预算约为 `16.67 ms`，120 FPS 约为 `8.33 ms`。
- 书中的四段式是功能模型；实际硬件会并行、重叠或拆分这些功能。

## 2.2 应用阶段

### 职责

应用阶段通常在 CPU 上运行，负责在每一帧中：

1. 读取输入并更新游戏/应用逻辑。
2. 更新相机、动画、物理、碰撞和场景物体的变换。
3. 执行可见性判断，例如视锥剔除。
4. 整理可见物体所需的网格、材质、纹理和参数。
5. 提交 draw call 或间接绘制命令给 GPU。

### Draw Call

一次 draw call 可以理解为 CPU 对 GPU 的指令：使用当前 shader、资源和渲染状态，绘制某个网格或其一部分。

常见状态包括：

- Shader / Pipeline State；
- 顶点和索引缓冲；
- 纹理、常量缓冲、材质参数；
- 深度、混合、剔除等渲染状态。

### 性能结论

- 过多小物体或不同材质，常导致 CPU 被 draw call 和状态设置拖慢。
- 对相同网格、相同材质的多个实例，可用 instancing 降低调用次数。
- CPU 可做粗粒度剔除；现代 GPU-driven 渲染也会在 GPU 上做实例或 cluster 级剔除。

## 2.3 几何处理

### 顶点的空间旅程

```text
模型空间（Local / Model）
  → 世界空间（World）
  → 观察空间（View / Eye）
  → 裁剪空间（Clip）
  → NDC
  → 屏幕/窗口坐标（Screen / Window）
```

概念上可写为：

```text
clipPosition = Projection × View × Model × localPosition
```

矩阵库可能采用不同的向量约定，导致代码中的乘法顺序不同；空间变换的概念顺序不变。

### 顶点着色器

Vertex Shader 的职责不只是“计算顶点光照”，更准确地说是加工每个顶点的数据：

- 必须输出顶点位置；
- 还可输出 UV、法线、顶点色、切线、世界坐标等；
- 输出数据会在光栅化时插值，供像素着色器使用。

### 投影、裁剪、NDC

- 正交投影：远近不改变大小，平行线保持平行。
- 透视投影：远处物体更小，来自透视除法。
- 投影后先得到齐次裁剪坐标 `(x_clip, y_clip, z_clip, w_clip)`。
- 裁剪在 Clip Space 中完成，完全在外的图元丢弃，部分相交的图元被切出可见部分。
- 然后执行透视除法：`(x/w, y/w, z/w)`，得到 NDC。
- NDC 再经 viewport 变换，映射到具体分辨率的窗口坐标。

### 可选顶点处理阶段

- Tessellation：根据距离等条件增加或减少曲面三角形密度。
- Geometry Shader：按图元生成有限的新顶点，曾常用于粒子等用途。
- Stream Output：将 GPU 处理后的几何输出到缓冲区供后续使用。

这些不是理解基础光栅管线的前提；现代引擎也经常以 Compute、Mesh Shader 或 GPU-driven 流程替代其中部分用途。

## 2.4 光栅化

光栅化把屏幕空间中的点、线、三角形转成一批片元（fragment）。它并不计算最终颜色。

```text
三角形顶点 + 每顶点数据
  → Triangle Setup：计算边与插值所需数据
  → Triangle Traversal：判断哪些采样点被覆盖
  → 片元：深度 + 插值后的 UV、法线、颜色等
```

- 最简单的覆盖规则是“像素中心在三角形内”。
- MSAA 使用每像素多个采样点，改善边缘锯齿。
- UV、法线和深度等属性会从三个顶点插值到每个片元。
- 透视正确插值会利用投影时保留的 `w`，避免倾斜表面上的纹理错误扭曲。

## 2.5 像素处理与合并

```text
片元
  → Pixel Shader：纹理采样、材质和光照计算
  → Merging / ROP：深度、模板、混合与写入缓冲
```

### Pixel Shader

- 接收插值后的 UV、法线、位置等数据。
- 采样纹理并计算材质、光照，输出一个或多个颜色结果。
- 运行频率通常是每片元或每采样点一次；覆盖面积越大、分辨率越高、shader 越复杂，代价越高。

### 深度、模板和混合

- **Depth Buffer（Z Buffer）**：保存当前最近表面的深度；不透明物体通常开启深度测试和深度写入。
- **Stencil Buffer**：每像素标记，可制作掩码、传送门、描边等效果。
- **Alpha Blending**：将新片元颜色与已存颜色混合；透明物体通常在不透明物体之后，从远到近渲染，并关闭深度写入。

### 性能：Overdraw

如果一个屏幕位置的片元多次被完整着色，但前面的结果随后又被更近物体覆盖，就发生了过度绘制。Early-Z 会尽量在执行昂贵像素着色器前剔除已知不可见的片元；使用 `discard`、修改深度或某些透明流程会限制它的效果。

### 显示

- GPU 通常向 Back Buffer 渲染，而不是直接修改显示器上的当前画面。
- 完成后通过 Present / Swap 显示这一帧；现代 API 通常用 Swap Chain 管理这些缓冲。

## 2.6 一帧的完整路径

```text
输入 / 时间
  → CPU 更新相机、动画、物体矩阵与可见性
  → 提交可见图元与绘制命令
  → GPU 变换顶点、投影和裁剪
  → 光栅化生成片元并插值属性
  → 像素着色器采样纹理、计算材质和光照
  → 深度/模板/混合决定最终缓冲内容
  → Present 到屏幕
```

关于“纹理应用”的精确分工：光栅化负责插值 UV；纹理采样通常发生在像素着色器中。

## 易混淆概念

| 概念 | 含义 |
| --- | --- |
| 剔除（Culling） | 整个图元/物体不需要画，直接跳过。 |
| 裁剪（Clipping） | 图元部分可见，沿视锥边界切出可见部分。 |
| 像素（Pixel） | 屏幕上的最终离散位置。 |
| 片元（Fragment） | 光栅化后等待测试/合并的候选结果，未必真的成为最终像素。 |
| Clip Space | 透视除法之前、用于裁剪的齐次坐标空间。 |
| NDC | 透视除法之后的归一化坐标空间，再映射到实际屏幕。 |

## 问答记录

### Q1：为什么大量不同材质会导致状态切换和 draw call？为什么影响性能？

**答：** 一个材质不仅是一张贴图，还通常包含 shader、纹理、常量参数以及深度、混合、剔除等状态。绘制使用不同材质的物体时，CPU 往往要重新设置或绑定这些状态并发出新的 draw call。

- CPU/驱动需要准备、验证和记录更多命令；调用数很高时，GPU 可能等待 CPU 继续提交工作。
- GPU 更适合连续执行相同的 shader 和资源绑定；频繁切换会降低批处理机会，并可能降低缓存利用率。
- 解决思路包括按材质排序、合批和 instancing。透明物体通常需由远到近绘制，不能随意按材质排序。

### Q2：NDC 是什么？

**答：** NDC（Normalized Device Coordinates，归一化设备坐标）是顶点完成投影、裁剪和透视除法后所在的标准化坐标空间。x、y 通常落在 `[-1, 1]` 内；z 的约定因 API 而异，DirectX/Vulkan 常用 `[0, 1]`，传统 OpenGL 常用 `[-1, 1]`。

```text
Clip Position：(x_clip, y_clip, z_clip, w_clip)
NDC：(x_clip / w_clip, y_clip / w_clip, z_clip / w_clip)
```

NDC 与实际窗口分辨率无关；随后 viewport 变换才会把它映射到如 1920×1080 的像素坐标。
